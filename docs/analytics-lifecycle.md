# Self-service analytics lifecycle

How this platform implements LLM self-service analytics that holds up in
production, generated by the `analytics-app` template. The design follows
the published Anthropic playbook — 95%+ answer accuracy came from
structural simplification, not clever prompting — mapped onto this
platform's Databricks + MLflow stack with one deliberate difference: the
semantic layer is **neutral and repo-owned**, so nothing below depends on a
specific warehouse.

The three failure modes every layer defends against:

1. **Concept ↔ entity ambiguity** — the agent cannot map "revenue" to the
   right definition when many plausible candidates exist.
2. **Staleness** — definitions, docs, and schemas drift apart silently.
3. **Retrieval failure** — the right context exists but is never found.

## The four layers

```text
1. data foundations   seeded canonical tables, grain/owner/freshness metadata
2. sources of truth   semantic layer FIRST -> curated references -> raw last
3. skills             knowledge router (thin index, docs on demand) + runbook
4. validation         snapshot-pinned golden evals, judges, provenance, gates
```

### 1. Data foundations

A generated project ships a small canonical star schema as a versioned
snapshot (`evals/data/seed_data.json`) that `jobs/seed_lakehouse.py` loads
idempotently — including fixed `_loaded_at` stamps, never `now()`, so
freshness behavior is reproducible. Real deployments replace the demo
tables but keep the discipline: one governed dataset per concept, with
grain, ownership, and freshness SLAs declared in the semantic model rather
than tribal knowledge.

### 2. Sources of truth — the neutral semantic layer

`semantics/semantic_model.yml` is a git-versioned contract: sources (table,
grain, owner, freshness SLA, gotchas), dimensions (columns, encodings,
declared joins), and metrics (aggregation, expression, structured filter,
description). Definitions are **human-curated** — auto-generating them from
tables re-encodes the ambiguity the layer exists to remove.

Strict Pydantic models validate the contract; a pure-Python compiler
renders a deliberately narrow grammar (standard aggregates, equality and
time-bucket filters, `DATE_TRUNC`, `GROUP BY`, `LIMIT`, parameterized
values) to SQL. The agent's `query_metrics` tool accepts only this plan
shape — the semantic-first rule is structural, not a convention.

Execution hides behind a three-method protocol:

```python
class WarehouseExecutor(Protocol):
    dialect: Dialect
    def run_plan(self, model, query) -> QueryResult: ...      # governed path
    def execute(self, sql, *, parameters=(), row_limit=1000) -> QueryResult: ...
    def latest_loaded_at(self, model, source_name) -> str | None: ...
```

Shipped implementations: `DatabricksWarehouseExecutor` (statement-execution
API through the certified SDK, `native_client` escape hatch, read-only
guard, LIMIT enforcement) and `FakeWarehouseExecutor` (a pure-Python plan
interpreter over the versioned snapshot — the reason evaluations run
credential-free). **Snowflake or any other SQL warehouse is an
application-code implementation of the same protocol**; the compiled
grammar is already portable, so no platform change is involved.

Because the layer lives in git rather than in a warehouse:

- definitions, docs, and eval cases ship in one reviewable diff;
- compiled-SQL snapshot tests and golden-value checks run in pull-request
  CI with zero credentials;
- the trade-off is honest: warehouse-native BI surfaces cannot see these
  metrics. The intended remedy is an exporter that projects the same
  contract outward (Unity Catalog metric-view DDL, dbt MetricFlow YAML) —
  one source, many projections — rather than a second hand-maintained copy.

### 3. Skills — knowledge router and runbook

`knowledge/*.md` are curated reference docs with YAML front-matter naming
the tables and metrics they cover, and a fixed skeleton: Grain, Scope,
Exclusions, Encodings, Gotchas, Common patterns, Cross-references. The
router (`src/app/knowledge.py`) indexes only the front-matter; the system
prompt carries the one-line-per-doc index and the compact metric catalog,
and a full document enters context only when the agent calls
`lookup_reference`. The published ablation is the reason: handing the agent
grep over thousands of SQL files moved accuracy by under 1% — routing beats
dumping.

The runbook (`prompts/system_prompt.json`) encodes the senior-analyst
process: clarify ambiguity → semantic layer first → reference docs →
guarded read-only fallback (labelled as such) → freshness check when it
matters → answer with caveats. The optional adversarial reviewer
(`src/app/reviewer.py`) re-derives the answer from recorded evidence;
production measurement of this pattern showed roughly **+6% accuracy for
+32% tokens and +72% latency**, so it ships opt-in and off by default.

**Anti-staleness is CI, not discipline**: `evals/offline_checks.py` fails
when any front-matter reference names a table or metric the semantic model
no longer defines. Change the model, the docs, and the evals together, in
one PR — the colocation practice that keeps skills from decaying.

### 4. Validation

Every answer ends in a **provenance footer rendered by code from
tool-recorded evidence** — the model can neither fabricate nor omit it:

```text
[provenance]
tier: semantic_layer
sources: <catalog>.<schema>.analytics_orders
owner: group:data-platform-owners
rows: 1
value: 600.75
sql: SELECT SUM(CASE WHEN `status` <> 'C' THEN `amount` END) AS `revenue` ...
[/provenance]
```

Five deterministic scorers grade that discipline in both tiers:
`routing_tier_match`, `provenance_complete`, `sql_read_only`,
`execution_match` (numeric answer vs the snapshot-pinned expectation), and
`semantic_share` (the monitored fraction of answers resolved through the
semantic layer). Tier 2 adds Correctness and Safety judges on a governed
Databricks endpoint, baseline regression, and cost coverage.

## Eval-set design

The golden set (`evals/data/golden_cases.json`) is built from the two
question families the playbook identifies:

- **Stakeholder questions** (the dashboard-shaped ones): metric lookups and
  grouped breakdowns with exact `expected_value`s pinned to the seed
  snapshot — never to live data — so truth does not rot as tables grow.
- **Long-tail questions**: encoding traps (the concept↔entity failure
  mode), ambiguity that must trigger clarification, freshness checks, a
  sanctioned raw fallback, and an out-of-scope refusal.

Each case carries `expected_tier`, an `expected_query` plan (compiled and
executed offline to prove the pinned value), and a category; offline CI
enforces minimum size and category coverage. The shipped fourteen cases are
a floor: grow toward **dozens per domain** — measured returns diminish
beyond that — by harvesting corrections (below). Gate thresholds mirror the
published ~90% per-domain launch bar, with provenance and read-only as hard
1.0 invariants.

Two practices keep the set honest:

- **Ablation, not vibes.** Before merging a structural change (new docs, a
  prompt edit, budget changes), run the gate before and after on the same
  cases and put the delta in the PR. `evals/baseline.json` plus
  `max_regression` automates the "did we get worse" half.
- **Correction harvesting.** Every wrong answer a human corrects becomes,
  in one PR: a new golden case, a gotcha line in the matching knowledge
  doc, and (when definitional) a semantic-model change. Deliberately boring
  — that is what makes domain owners actually do it.

## Tokenomics

Cost is a governed output of the system, not a surprise:

- The agent accumulates a per-answer `TokenUsage` from provider usage
  payloads, split into main-loop and review-pass tokens.
- The release gate enforces **cost coverage**: `evals/evaluate.py` computes
  `cost/coverage` (share of answers with captured usage) and applies
  `GatePolicy(minimum_cost_coverage=0.9)`, so cost-blind answers fail the
  gate; `tokens/mean_total` and `tokens/mean_review` are logged per run to
  chart cost against accuracy over time.
- The adversarial reviewer is the one deliberate cost lever (+~32% tokens,
  +~72% latency for +~6% accuracy) — enable it per environment via the
  template input or `AAI_ANALYTICS_ADVERSARIAL_REVIEW`, and let the logged
  review tokens show what it costs you.
- Endpoint-side attribution needs no application code: the platform SDK
  injects AI Gateway request tags (application, team, cost center) on every
  model call, which is how answers roll up in billing usage tables.

## Context engineering

The context budget is explicit and centralized (`src/app/config.py`):

- system prompt = runbook + compact metric catalog + knowledge index
  summary — never the full semantic YAML, never whole documents;
- reference docs load on demand and cap at `MAX_REFERENCE_DOC_CHARS`;
- result sets truncate to `MAX_RESULT_ROWS_IN_CONTEXT` with the true
  `row_count` stated, so the agent says "showing 20 of 3400" instead of
  silently analyzing a truncation;
- the tool loop is bounded at `MAX_AGENT_TURNS`;
- answers are single-question scoped in v1 — no long conversational memory
  to leak stale context between questions.

The four teaching notebooks walk these layers on the shipped snapshot,
credential-free: `01_explore_semantics`, `02_context_engineering`,
`03_run_the_agent` (including per-pass token accounting), and
`04_evaluate_and_gate`.

## Lifecycle commands

Generate a project (from the platform console, or directly — inside a
checkout of this monorepo `databricks bundle init ./templates/analytics-app`
works too):

```bash
az login
source scripts/platform-env.sh
databricks bundle init "$AAI_TEMPLATE_REPO" \
  --template-dir templates/analytics-app --output-dir my-analytics
cd my-analytics
python3.12 scripts/setup_dev.py
```

Then, inside the generated project:

```bash
make check
databricks bundle deploy -t dev
databricks bundle run release_gate -t dev
```

`make check` runs lint, the hermetic tests, and the tier-1 offline gate.
The `release_gate` job seeds the snapshot into the warehouse, then runs the
tier-2 judged evaluation with `--warehouse-id` supplied by the bundle
variable.

## Provision externally (platform-owned, one-time)

Per the platform's bootstrap rule, none of this is created by the template,
its CI, or application code — request it through the approved platform
process:

| Prerequisite | Detail |
|---|---|
| SQL warehouse | `CAN USE` for the deploying identity on a small serverless warehouse with a short auto-stop; the id becomes the `warehouse_id` bundle variable |
| Demo schema | `USE CATALOG` on the chosen catalog; `USE SCHEMA`, `CREATE TABLE`, `MODIFY`, `SELECT` on the chosen schema for the seed job |
| Model endpoints | `CAN_QUERY` on the chat endpoint and the judge endpoint (judges always route through a governed Databricks endpoint) |

A missing grant fails fast: the release gate preflights `SELECT 1` on the
warehouse before spending a single model token.

## Extending to another warehouse

Implement the `WarehouseExecutor` protocol in the generated project's
application code — `run_plan` may simply call the shared compiler and your
`execute`; `latest_loaded_at` is one `MAX(loaded_at)` query. Keep the
read-only guard on the fallback path, return `QueryResult` values as
strings, and the agent, scorers, gates, and notebooks work unchanged. The
platform deliberately ships no second adapter until one is certified:
adding a connector dependency is a dependency-policy change, not a code
drop.

## Roadmap notes

- **Exporters, not copies**: project the semantic contract to Unity Catalog
  metric views / dbt MetricFlow YAML for BI-surface visibility.
- **Serving**: this template is job + notebook scoped; serve the agent over
  HTTP by graduating to the agent-app pattern (MLflow Agent Server on
  Databricks Apps).
- **SDK promotion**: the semantic engine stays template-owned while it
  proves out (`compatibility.json` records the feature as
  `self_service_analytics: preview`); promotion into `aai-core` is a later,
  deliberate API decision.
